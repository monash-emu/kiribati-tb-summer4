# summer4 workarounds

Every place this port works around a summer4 API, with the reason. Code carries a matching
`# WORKAROUND(summer4): ...` comment. summer4's roadmap step 21 handoff reads this list so the
next summer4 package can absorb them. Row IDs refer to summer4's `docs/evaluation/tb-ports.md`
(`KI*`) and `docs/evaluation/composability.md` (`CX*`).

## Workarounds

| # | Phase | File | What | Why | Relates to |
| --- | --- | --- | --- | --- | --- |
| W1 | K2 | `src/kiribati_tb/model.py` (`POOL`, `pmap`, `force_of_infection`) | With homogeneous mixing the map carries a one-trait property `pool` and the force of infection groups by it. | `ForceOfInfection` requires `group_by: Property`. summer2's homogeneous model has one mixing category (`I_total / N_total ** exp`); grouping by age or reachability would give per-group denominators instead, and no constant mixing matrix reproduces a single pool under a generalised exponent. | `KI4`; suggest `ForceOfInfection(group_by=None)` meaning one pool |
| W2 | K3 | `src/kiribati_tb/outputs.py` (`add_computed_values`) | The original's three computed values (`passive_detection_rate_clin`, `passive_detection_rate_subclin`, `mixing_matrix_distance`) are `SaveFn` leaves that recompute the value from the save time and the prepared parameters, duplicating the detection rate tree in plain JAX (both checked against the goldens). | summer4 cannot save the value of an ungrouped rate expression: `Capture`/`GroupedOutput` need a `GroupedRate`, and `ComputedValue` needs a `derived_fn` that runs in every vector-field call to produce values only the outputs read. (A clean timing showed no measurable `derived_fn` cost here, so this is about idiom, not speed.) | `KI12`; suggest a save quantity for a rate expression, e.g. `SaveRequest(Rate(expr))` evaluated at save times |
| W3 | K4 | `src/kiribati_tb/calibration.py` (`OutputTargets`) | A `TargetSet` subclass whose `plan()` returns the save plan unchanged. | `BayesianModel._build_save_plan` folds `targets.plan()` in before `outputs.plan()`, and `Target.contribute` raises unless the key is already a save key or the target carries a leaf `quantity`. Every Kiribati target is a derived `OutputSet` name (`..._per100k`, `..._perc`, `notifications`, `mixing_matrix_distance`), and derived names are never save keys, so the stock `TargetSet` cannot be used with `outputs=`. The outputs already plan every leaf the targets read, and `log_likelihood` reads targets from the evaluated outputs. | `KI18`: `KI18` is marked `full` but no summer4 test scores a target on a derived output. Suggest `BayesianModel` plan outputs first and let `Target.contribute` accept keys that name an `OutputSet` output |
| W4 | K5 | `src/kiribati_tb/analysis.py` (`averted_quantiles`) | Averted-burden quantiles are computed from `PosteriorRuns.samples` rather than `PosteriorRuns.differences`. | `differences` returns quantiles of `scenario − ref` (relative: divided by `ref`). The original's `diff_quantiles_df_*` files hold quantiles of `ref − scenario` (averted burden, positive when screening helps), and quantiles do not commute with negation, so the summer4 frame cannot be flipped after the fact. | `KI21`; suggest a `sign=`/`averted=True` option on `differences` |
| W5 | K5 | `src/kiribati_tb/outputs.py` (`restrict_outputs`), `analysis.py` | Full runs record an `OutputSet` whose keys are only the 137 outputs the original saved; every intermediate they read is inlined into their expressions. | `posterior_runs` records every key of the scenario's `OutputSet` for every draw and requires the same key set in every scenario. The original's intermediates include the per-program screening flows, which differ between scenarios, and recording all ~680 outputs for 1,000 draws costs ~1 GB per scenario. | `KI21`; suggest a `record=` list of output names on `posterior_runs` |
| W6 | K4b | `src/kiribati_tb/pipeline.py` (`forward_log_density`), `scripts/bench_gradients.py` | The log density of a model solved with `Diffrax(adjoint=diffrax.ForwardMode())` is built with `numpyro.infer.util.initialize_model(..., forward_mode_differentiation=True)` instead of `BayesianModel.potential_fn`. | `BayesianModel._ensure_potential` (`epi/calibration/model.py:219` at `c9548d5`) calls `initialize_model` without `forward_mode_differentiation`, and its valid-start check takes a reverse-mode gradient, which fails through a forward-mode solve: `ValueError: Reverse-mode differentiation does not work for lax.while_loop or lax.fori_loop with dynamic start/stop values. Try using lax.scan, or using fori_loop with static start/stop.` So `potential_fn`, `log_density`, `wf.evaluate` and `wf.optimize` are all unusable with the forward-mode adjoint. The port needs forward mode where reverse-mode gradients are NaN (S5). | `CX*` (composability of the solve and the potential). Done when `BayesianModel` takes `forward_mode=True` (or reads it off the solver's adjoint) and passes it to `initialize_model`, and `wf.Optax` uses `jax.jacfwd` for such a model |
| W7 | K4b | `src/kiribati_tb/pipeline.py` (`lbfgs`) | Multi-start optimisation is scipy L-BFGS-B, one host loop per start over a jitted value-and-gradient, with starts run concurrently in threads (8 workers: 24 starts in 285 s). | `wf.optimize` vmaps all starts into one compiled program (`OptimizeRun`, `_run_chunk_vmap`, `workflow/optimize.py:327`). With an adaptive solver every lane runs to the slowest lane's step count, and with a line search to the slowest lane's line search. An `optax.lbfgs` `OptimizeMethod` (the public protocol accepted it) did not finish one 10-step chunk for 24 starts in 18 minutes. `wf.Optax` cannot drive `optax.lbfgs` at all: its step calls `tx.update(grads, state, z, value=loss)` (`optimize.py:161`) without the `value_fn` the zoom line search needs. | `CX16`–`CX19` (optimiser composability). Done when `optimize` can map starts other than by `vmap` (`lax.map`, threads, or `pmap` over host devices) and `Optax` passes `value_fn=` |
| W8 | K4b | `src/kiribati_tb/pipeline.py` (`Checkpoint`, `save_warmup`, `load_warmup`) | Chunked NUTS is checkpointed by the stop callable: after every chunk it reads the caller's `mcmc` (`get_samples`, `get_extra_fields`, `last_state`), writes `idata.nc`, the pickled sampler state and `progress.csv`, and decides on rank-normalised split R-hat and bulk **and tail** ESS (arviz) over every draw since the first start. `Checkpoint.resume` reloads the draws and gives a fresh `MCMC` the saved state as `post_warmup_state`. | `wf.MCMCRun` lives only in memory: no `save`/`load`, and resuming in a new process means reaching into its private `_sample`/`_decide` or losing the earlier draws from the stop rule's diagnostics. `StopRule` sees only numpyro's classic split R-hat and bulk ESS (`workflow/mcmc.py:94-119`), not tail ESS or rank-normalised R-hat, and a stop callable is handed a progress row, not the draws. `warmup_until` is not checkpointed either. | Done when `MCMCRun.save(path)` / `MCMCRun.load(path, mcmc)` exist and `StopRule` can require tail ESS |
| W9 | K4b | `src/kiribati_tb/pipeline.py` (`RidgeShear`, `nuts_factory(shear=)`) | NUTS runs on `NUTS(potential_fn=shear.potential(bm))` in sheared coordinates, with draws mapped back by `bm.constrain(shear.inverse(w))` in the checkpoint. | `BayesianModel.numpyro_model` samples every prior in its own bijector (`biject_to(support)`), with no hook to change coordinates jointly. The transmission ridge (`raw_transmission_rate` against `infection_pop_scale`) is thin and curved in those coordinates. Running NUTS on a potential function loses numpyro's `postprocess_fn`, so the constrained draws are rebuilt by hand. | Done when `BayesianModel` (or `wf.sample_until`) accepts a coordinate map (a numpyro `Reparam` or a bijection of the unconstrained vector) and returns constrained draws |

## Sharp edges met (no workaround needed)

Places where summer4 did what was asked but a port could easily get wrong. Recorded so summer4
can decide whether to change a default or its documentation.

| # | Phase | Where | What happened | Suggested summer4 change |
| --- | --- | --- | --- | --- |
| S1 | K1 | `model.py` `SUMMER2_SIGMOID_CURVATURE` | summer2's `get_sigmoidal_interpolation_function` defaults to curvature 16; summer4's `sharpness` (documented as "summer2's curvature parameter") defaults to 1, which is near-linear. Porting the call without the argument moved the population by up to 3.6 persons per compartment (7e-4 relative) after 1950. Passing `sharpness=16.0` gives 1e-9 agreement (`tests/test_demography.py`). | Say in `sigmoidal` / `Data.interp` / `TableData.interp` docstrings, and in the summer2 migration page, that summer2's default is 16. |
| S2 | K1 | `kiribati_tb/__init__.py` | summer2gen runs in float64 (computegraph enables `jax_enable_x64`); summer4 does not. The port enables it on import, as `tb-macro-summer4` does. | Document float64 as the parity setting for summer2 ports. |
| S3 | K1–K2 | `model.py` `SOLVER_KWARGS`, `reference/make_golden.py` | The yearly mixing matrix (a `Lookup` on `floor(Time() - 1850)`) jumps at every integer year. At `rtol = atol = 1e-8` both summer2gen's `odeint` and diffrax's `Dopri5` carry ~1.5e-5 relative error from the jumps, above the 1e-5 parity bar, so goldens and parity runs use `1e-10` (port within 1.5e-7 of the original). summer2gen also caps the step at one year; `CompiledModel.run` in v0.2.0a5 builds its own `PIDController` with no `dtmax` or `jump_ts`, and neither is needed at 1e-10. | Telling the controller about the yearly jumps (`jump_ts`) would let a port run at looser tolerance; summer4 `main`'s CP1 lets `run()` take the caller's controller, so this is available from the next tag. |
| S4 | K4 | `notebooks/04-calibration.ipynb` | With numpyro 0.22 and arviz 1.x (the versions pixi resolves for summer4 v0.2.0a5), importing `arviz` before `numpyro` leaves `numpyro.distributions` half-initialised, and the first `BayesianModel` log-density evaluation fails with `module 'numpyro.distributions' has no attribute 'distribution'`. Importing `numpyro` first avoids it. | Import numpyro in `summer4.epi.calibration` at import time (or pin arviz), and note it in the calibration docs. |
| S5 | K4b | `kiribati_tb/calibration.py` (`forward_mode_solver`), `pipeline.lbfgs(fallback=)` | Reverse-mode gradients of the adaptive solve are NaN (every model parameter) at 17% of 256 prior design points, though the log density there is finite; forward mode (`diffrax.ForwardMode`) is finite at the same points. The NaN appears in diffrax's checkpointed-while-loop backward pass (`jax_debug_nans`), not in the vector field's VJP at accepted states, and a constant step size removes it: a *rejected* trial step evaluates the vector field at an invalid state and its `0 * nan` cotangent survives the `where` that discards the step. Not localised to one op; `n_grp ** exponent` on a negative trial population in the generalised force of infection (`epi/infection.py:452`) is a likely source. None of 96 published posterior draws is affected, so NUTS in the posterior bulk uses reverse mode (0.18 s against 0.26 s forward). | Guard the power (`maximum(n_grp, 0) ** exponent`) or document forward mode as the fallback for adaptive solves |
| S6 | K4b | `kiribati_tb/calibration.py` (`CALIBRATION_SOLVER["max_steps"]`) | `default_max_steps` (`solvers/base.py:19`) allows 64 steps per unit `dt`: 11,840 for 1850–2035, against 650–850 for a plausible parameter set. A pathological proposal then costs up to 16× a normal solve before it is scored as a failure (one L-BFGS start spent 238 s on 42 evaluations). The port caps it at 4,096. | A tighter default, or say in the `run` docstring that calibration should set `max_steps` |
| S7 | K4b | `kiribati_tb/pipeline.py` (`nuts_factory(inverse_mass_matrix=)`) | NUTS started from the identity metric on this posterior needs 255-leapfrog trajectories (about 40 s per iteration) until its first mass-matrix window closes at iteration 75+. `wf.warmup_until` carries only positions between rounds (`workflow/warmup.py:255`), so each failed round restarts from the identity metric and repeats that cost. The port passes a Laplace covariance as `inverse_mass_matrix`. | Carry the last round's adapted metric (and step size) into the next round's kernel |
| S8 | K4b | `scripts/find_map.py`, `scripts/synthetic_recovery.py` | Re-pinning summer4 from `v0.2.0a5` to `c9548d5` changed `BayesianModel.find_map` to return an `OptimizeRun` (`.best_params`) and `BayesianModel.sample` to return an `MCMCRun` (`.idata`). Two call sites updated. | None (intended CP2 change); noted for other ports |
